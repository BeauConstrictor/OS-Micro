# FS/128-3

FS/128-3 is a modification of the FS/128-2 spec that is fully backwards-compatible, but allows for multiple directories (meaning the filesystem is no longer flat).

The primary goal of FS/128-3 is to allow existing implementations of FS/128-2 to add support with as few modifications to existing code as possible.

## The Change

The root directory in sector 2 is no longer special - it is a directory like any other, and other directories in other sectors can be listed just the same (they have the same structure).

Directories can contain entries referencing other directories, as normal file entries, but the filename must end with a single `/`. FS/128-3 also bans the `/` character in regular filenames.

Since regular files treat the final byte in a sector as a 'link' to the next data sector and directories treat that byte the same as every other byte, you should not try to read directories as regular files.

For a filesystem using the FS/128-3 features, all directories must contain a `./` entry that points back to itself and a `../` entry that points to the 'parent directory'. In the root directory, `../` should also point back to itself, as there is no parent. The presence of these entries in sector 2 is how FS/128-3 is identified. Technically, FS/128-2 can also contain entries with these names, but that is beyond the scope of this implementation (maybe but some magic number in the reserved sectors?). The `./` must always be the first entry in the directory and the `../` should always be the second.

This spec intentionally does not define a way of looking up files with paths, although it shouldn't be hard to implement this - how paths are structured (Unix-style with a single root and mount points or Windows-style with drive letters) is irrelevant to the filesystem.

Just like how multiple directory entries to the same file are disallowed in FS/128-2, the same applies across all directories in FS/128-3. Also, besides, the special `./` and `../` entries, there should only be a single entry that in any directory that points to any other directory. Essentially, this constraint ensures that the filesystem follows a tree structure, not a free graph with the pain of cycles and multiple parents.

Implementations should reject attempts to delete `./` and `../` directories entirely, and attempts to delete other directories should recursively traverse the directory and any sub-directories and delete all contained files too.

## Example

Root directory:

```
./   -> <root>
../  -> <root>
bin/ -> bin/
test.txt
```

`bin/` directory:

```
./   -> bin/
../  -> <root>
pager
```

## Compatibility

An FS/128-2 reader should handle this just fine (although only seeing files in the root directory of course), so long as you don't try to read the contents of a directory as a file. An FS/128-3 reader could handle the majority of FS/128-2 filesystems too, but might stumble on regular files that for some reason end in a slash (allowed in FS/128-2).
